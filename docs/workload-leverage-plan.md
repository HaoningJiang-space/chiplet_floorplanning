# 最优布局是否随工作负载改变（计划，运行前冻结）

## 问题

[封装杠杆检验](package-leverage-plan.md)表明，布局与封装在温度层面基本可分。另一个可能的交互来源是工作负载：
ATPlace 案例只给每个芯粒一个固定功耗，而真实系统在不同负载下各芯粒的功耗比例会变。布局最依赖的正是"谁和谁热"，
所以要问：**按名义功耗图选出的最优布局，在其他负载下还是最优吗？若不是，损失多少 K？**
只有当这个损失明显大于算法之间的差别（以往十多次比较都在 0.5 K 以内），"一个布局服务多种负载"才可能成为新问题。

## 文献核查（2026-11-15，初步）

- **多功耗图引导的布局在 3D IC 上有先例**：按一组代表性基准的功耗剖面引导 3D 多处理器 floorplan，比按最坏情况设计的热指标更好（Springer 2011，"Power Profiling-Guided Floorplanner"）；
  3D floorplan 与电压分配联合，覆盖高性能和低功耗两种剖面（ACM TODAES 2017）。
- **非均匀功耗的影响**：2.5D/3D 研究（arXiv 2508.02284）指出均匀功耗假设会掩盖负载驱动的热点。
- **芯粒布局**（TAP-2.5D、ATPlace、MaskPlace2.5D、ATMPlace 等）都只用一张功耗图；未见针对 2.5D 芯粒、多负载的布局工作。
- **实测功耗拆分**：芯粒级、逐负载的实测功耗很少。能找到的只有 H100 长上下文推理的整卡功耗 693 W，以及 HBM 小于 200 W 的估计，
  所以下面的负载场景只能是声明的活动系数，不是测量值。

## 方法（冻结）

- 评估集与核对同封装检验：十例前沿 1340 个布局、基准封装、名义功耗峰温须与冻结前沿一致（≤1e-6 K）。
- 芯粒类别按名称前缀：计算 = CPU*、GPU、Virtuvian；存储 = HBM、DRAM；其余（Analog、MEMS、IODie、Nimbus、DUMMY）始终保持名义功耗。
- 负载场景（活动系数，相对名义功耗）：

  | 场景 | 含义 | 系数 |
  | --- | --- | --- |
  | memory_idle | 计算密集 | 存储 ×0.3 |
  | compute_half | 访存密集 | 计算 ×0.5 |
  | gpu_idle / cpu_idle | 只用 CPU / 只用 GPU | GPU / CPU* ×0.2 |
  | odd_idle / even_idle | 同类计算芯粒只用一半 | 同类有 ≥2 个的计算芯粒，编号奇 / 偶者 ×0.2 |

  把全部计算芯粒都闲置、或不改变任何芯粒的场景不计入。
- 两个功耗族：
  - **budget（主）**：封装功耗预算不变，释放的功耗按名义功耗比例分给仍满载的计算芯粒（睿频），每个最多 1.5× 名义，超出部分舍弃；
  - **activity（辅）**：只乘系数，不再分配。名义图是全满载，所以每个布局在任何 activity 场景下都不比名义热，
    按最坏情况的稳健布局就等于名义最优，这一族只回答"该负载下的最优布局是否不同"。
- 每例每场景：在长度不超过 1.25×Lmin 的前沿布局中，取该场景下最冷的布局 b_s；
  **后悔值** = 名义最优布局在该场景下的峰温 − b_s 的峰温。

## 判定（运行前写定，以 budget 族为准）

- **值得做**：至少 3 例有某个场景后悔值 ≥ 1.0 K（是以往算法差别的两倍以上）；
- **退化**：所有例、所有场景后悔值 < 0.3 K；
- 其余为**不确定**。activity 族按同一规则另报，不改变判定。

## 运行前估计

后悔值来自两件事：场景让一部分芯粒变冷后，名义最优布局里"为隔开它们而付出的距离"变得多余；
同时满载的芯粒因睿频更热，最优布局应该把它们彼此隔开，而名义布局未必这样做。
- 同类计算芯粒多、名义最优把它们均匀铺开的例子（Case3/5/4/9）：一半闲置后，活跃的一半可能在名义布局里挨得很近，
  预计 odd/even_idle 后悔值 1–3 K；
- 芯粒少、名义最优已经把每个热芯粒放在角落的例子（Case1/2）：预计 < 0.5 K；
- memory_idle 与 compute_half 主要改变总功耗，相对热分布变化小，预计后悔值小。
预测"值得做"或"不确定"；如果 1.25×Lmin 的长度上限把候选限制得太死，也可能"退化"。

## 局限

候选只来自名义功耗下筛出的前沿，各场景下真正的最优布局可能不在其中，所以后悔值只会被低估。
活动系数与睿频上限是声明值；判"值得做"后，需要借 CoMeT/HotSniper 等工具的负载与功耗轨迹换成有出处的场景，再建立降频与性能指标。
