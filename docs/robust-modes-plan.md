# 持续功耗模式下的鲁棒布局：最坏模式热裕量（开发计划，运行前冻结）

依据：[658f8e7 评估](overall-research-status.md)（"ee3c78e：持续功耗模式的鲁棒布局提案评估"）。

## 问题

芯片要求在一组**持续运行**的功耗模式下都不超温，同时连线尽量短。不需要各模式的出现频率。
固定互连上限 B（与之前相同，名义前沿最短长度的 1.25 倍）：

  J(x) = max_{m,i} [T_i(x, p_m) − T_i,max]，L(x) ≤ B。

T_i 为芯粒 i 内的最高功耗层温度。J ≤ 0 才算达标；降低 J 不等于达标，两者都报告。

问：只按满载优化的布局 N，与直接最小化 J 的布局 R 相比，J 差多少，满载峰温又付出多少？

## 模式集与校准（声明）

- 模式：名义（满载）加上 `workload_leverage.scenarios` 中适用于该例的全部 budget 场景（存储闲置、计算半载、GPU 闲置、CPU 闲置、
  同类芯粒半数闲置）。闲置芯粒取 0.2 倍名义功耗，空出的功耗按名义比例分给保持满载的计算芯粒，每颗上限为 boost × 名义，封装总功耗不超过名义。
- **boost 是声明假设，不是厂商校准值。** AMD MI300 Smart Shift、NVIDIA GH200 的功耗分配机制确认 CPU/GPU 可共享功耗预算，
  但没有给出任意芯粒的持续上限。所以 boost 取 1.0 / 1.25 / 1.5 三档做敏感性，问"boost 到多少时鲁棒布局开始值得做"。
  boost = 1.0 时闲置模式只降功耗，J 由满载决定。直接搜索只在 1.5 一档做。
- 温限：逻辑 105 °C，存储（HBM/DRAM）95 °C，声明值；其余芯粒按逻辑处理。
- 只覆盖**逻辑闲置**：芯粒材料保留，只改功耗图。物理少装会改变导热结构，不属于本计划。
- 稳态；不评价模式切换过程。

## 方法（冻结）

1. **交叉评估**（有已保存负载搜索结果的 8 例：Case1/2/3/4/5/6/9/10）：候选 = 冻结名义前沿 + `workload-search-v1.json` 中保存的
   名义搜索最优 N 与各场景最优布局。名义峰温须与冻结记录一致（≤ 1e-6 K）。在三档 boost 下计算全部候选的 J；
   在上限内比较 N 与 J 最小的候选。
2. **直接鲁棒搜索**（Case3、Case5 为正信号候选，Case9 为"单模式收益大、最坏模式未必受益"的对照；boost 1.5）：
   lp_epsilon 以 J 为目标，1000 个不同布局的预算、种子 2026111401、起点 48 个随机加 48 个长度下降、batch 48，
   与负载直接搜索（`9f56049` 的 `tools/workload_search.py`）的名义搜索完全相同。每个布局一次矩阵分解，各模式回代。
   R = 上限内 J 最小的布局，候选为交叉评估的全部候选加搜索结果；N = 已保存的名义搜索最优。
3. 报告：增益 = J(N) − J(R)；N、R 是否达标；反向代价 = T_满载(R) − T_满载(N)；R 的长度与各芯粒在最坏模式下的峰温。

## 判定（运行前写定，开发阶段，一个种子）

以直接搜索的三例为准：至少 2 例增益 ≥ 1.0 K 为"值得做"，再扩展到全部案例与第二个种子；全部 < 0.3 K 为"退化"；其余"不确定"。
交叉评估只作描述，报告各 boost 下的增益。

## 运行前修订（`082379a` 审查 `8d2be3d`，在任何结果出来前完成）

首次运行（`8d2be3d`）在第一个例子完成前停止，日志改名为 `*-prereview` 不采用。修订：

- **同温限的满载基线 L。** 原基线 N 最小化满载绝对峰温，鲁棒目标最小化相对各芯粒温限的超温，两者同时变化，收益不能全部归因于多模式。
  新增 L：只在满载模式下最小化 max_i(T_i − T_i,max)。交叉评估中 L 取候选里满载超温最低者；直接搜索中另跑一次以满载超温为目标的
  lp_epsilon（同起点、同预算、同上限），L 取候选与该搜索结果中满载超温最低者。鲁棒布局 R 的候选另含 L。
  **判定改用对 L 的增益**；对 N 的增益照旧报告。
- 基准布局超出互连上限时直接报错；没有直接搜索数据时判"无数据"，不判"退化"。
- 功耗挪移按名义功耗比例分配，名义功耗为 0 的芯粒不接收（原代码除以零）。当前十例没有零功耗计算芯粒，结果不受影响。
- 对运行前估计的更正：审查按完整模式集复算，已保存的场景布局在 Case3/5 被互补的 odd_idle 反超（最坏温度 144.19 / 155.29 °C，
  满载布局为 142.44 / 145.53 °C），所以"完整模式下增益不小于 6.1 / 4.0 K"不成立；直接搜索能否找到折中仍未知。

## 运行前估计

- 评估中按两模式复算：Case3 +6.14 K、Case5 +3.97 K、Case9 −4.20 K（场景布局反而更差）。完整模式集与直接搜索下，
  Case3、Case5 的增益应不小于这个量级，Case9 可能找到 0–2 K 的折中。预测"值得做"。
- boost 敏感性：1.0 时增益为 0；1.25 时预计 Case3、Case5 仍有 1–3 K。
- 风险：所有模式和芯粒都超过温限（J > 0），即鲁棒布局降低了超温但仍不达标；这在当前封装模型下很可能（名义峰温已在 100–136 °C）。

## 局限

- 模式集与 boost 为声明假设；ATPlace 功耗未校准；封装为声明的 TAP 族模型。
- 一个种子；搜索预算有限，后悔与增益依赖两次搜索各自的质量。
- 性能（盈亏平衡 q* = c/(g+c)）需要性能模型，本阶段不做。

## 结果（2026-11-15，eex005，`eea9c6c`，按修订后的冻结方法执行）

证据：[robust-modes-v1.json](evidence/robust-modes-v1.json)（每个候选的满载峰温、满载超温、三档 boost 下的 J，以及直接搜索的基线与鲁棒布局坐标）。
八例的前沿与保存布局的名义峰温均与冻结记录一致。

**判定（对同温限基线 L）：值得做（Case3 1.60 K、Case9 3.08 K，Case5 0）。对原峰温基线 N 的判定相同。**
但有三个限定，比判定本身更重要：

| 例 | J(L)：基线最坏超温 | J(R)：鲁棒布局 | 增益 | 反向代价（满载峰温） | R 的来源 | 是否达标 |
| --- | --- | --- | --- | --- | --- | --- |
| Case3 | 37.44 K | 35.84 K | **1.60 K** | +2.17 K | 冻结前沿 | 都不达标 |
| Case5 | 40.53 K | 40.53 K | 0 | 0 | 冻结前沿（与 L 同） | 都不达标 |
| Case9 | 26.97 K | 23.89 K | **3.08 K** | +4.34 K | 鲁棒搜索 | 都不达标 |

1. **全部不达标，而且差得远。** 三例在满载下就已超温 16–31 K（满载超温最低值：Case3 21.5、Case5 31.2、Case9 16.1 K），
   鲁棒布局只把最坏超温降低 1.6–3.1 K。在当前声明的封装与 ATPlace 功耗下，这些例子无论怎么布局都不能满足 105/95 °C，
   "热裕量"的提升没有转化为"能否达标"的差别。
2. **收益只在 boost = 1.5 时出现。** 交叉评估中，Case3/5/9/10 在 boost 1.0 与 1.25 下对 L 的增益都是 0；
   只有 Case6 在 1.25 时有 0.92 K。1.5 倍是声明假设，没有厂商校准，所以收益依赖的正是最不确定的那个参数。
3. **Case3 的鲁棒布局来自冻结前沿，不是鲁棒搜索。** 鲁棒搜索在 826 次后停滞，没有超过已有候选；Case9 的收益才来自鲁棒搜索本身。
   两例的反向代价（满载峰温 +2.2、+4.3 K）都大于增益，即这是真实的取舍。

交叉评估（对 L 的增益 / 基线 J）：

| 例 | boost 1.0 | 1.25 | 1.5 |
| --- | --- | --- | --- |
| Case1 | 0 / 0.8 K | 0.03 / 4.1 | 0.05 / 14.3 |
| Case2 | 0 / −25.6 | 0.07 / −21.8 | 0.07 / −21.1 |
| Case3 | 0 / 21.5 | 0 / 25.6 | 1.60 / 37.4 |
| Case4 | 0 / 13.2 | 0.20 / 14.0 | 0.30 / 22.4 |
| Case5 | 0 / 31.2 | 0 / 34.3 | 0 / 40.5 |
| Case6 | 0 / −4.8 | 0.92 / −0.6 | 0.99 / 4.0 |
| Case9 | 0 / 16.1 | 0 / 18.8 | 0 / 27.0 |
| Case10 | 0 / 3.0 | 0 / 3.0 | 0 / 10.4 |

- 对原峰温基线 N，boost 1.0 时 Case2、Case6 有 2.22、2.01 K 的"增益"，而对 L 为 0。这正是审查指出的目标函数差异：
  只是把"绝对峰温"换成"相对各芯粒温限"，不涉及多模式。修订后的判定已排除这部分。
- 只有 Case2、Case6 的基线可达标（J < 0），而 Case6 在 boost 1.25 时 L 已贴近温限（−0.6 K）；这里鲁棒布局（再低 0.92 K）
  是唯一可能让"达标与否"出现差别的地方。

**与运行前估计的对照。** 预测"值得做"按冻结规则成立；预测的风险"降低了超温但仍不达标"也成立，而且是三例全部。
修订中已撤回的"不小于 6.1 / 4.0 K"确实不成立：Case5 为 0，Case3 只有 1.6 K。

**含义与下一步。** 按冻结规则应扩展到全部案例与第二个种子，但在此之前应先回答两个更根本的问题，否则扩展没有意义：
- 封装与功耗口径：满载就超温 16–31 K，说明声明的封装散热或 ATPlace 功耗与"可持续运行"不相容。应先把每例的功耗缩放到满载恰好达标
  （或换用冷板），再问多模式能否在达标边界上改变结论；
- boost 校准：收益只在 1.5 倍出现，需要找到持续挪移上限的依据，或把"收益出现的 boost 阈值"作为主要结论报告。
